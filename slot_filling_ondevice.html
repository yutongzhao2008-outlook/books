① 为什么要做端侧槽位填充

隐私
语音、住址、银行卡相关的话语不离开手机。
延迟
不经过网络往返，本地即可出结果；网络差也能用。
离线
地铁、飞行模式、弱网场景下仍可工作。
成本
没有按 token 计费，也没有服务端并发压力。
代价是：内存、算力、模型能力都受限。端侧通常只能跑 0.5B–2B 级别的小模型，它们不会可靠地遵循长指令。所以端侧方案的关键不是“写更长的 Prompt”，而是让解码过程本身受约束，再由代码兜底校验。

② 三条开源路线

路线做法优点代价适合
A. 小 LLM + 约束解码
推荐		 GGUF 量化模型（如 Qwen2.5-0.5B/1.5B-Instruct、Gemma 3 1B、SmolLM2）+ llama.cpp，通过 json_schema / GBNF 语法约束输出 一个模型覆盖多槽位、改 Schema 即可扩展；能处理口语、省略表达 占用内存较多；需要做量化与基准测试 通用任务型对话，中高端机型
B. 小型 NLU 模型 BERT 类意图分类 + 序列标注（BIO）模型，导出为 ONNX / TFLite 在端侧运行 体积小、延迟低、结果确定 需要标注数据；新增槽位要重新训练 槽位固定、数据充足、低内存设备
C. 规则 + 词典 正则、日期解析、城市/车站词典、数字归一化 零模型、完全可解释 覆盖率有限，口语变体难处理 兜底、日期/数字归一化、低端机

⑥ 实现步骤

  
第一步：准备模型

  
    
    
  1. 选择小模型（如 Qwen2.5-0.5B/1.5B-Instruct），在可信环境中转换为 GGUF 并做量化（如 Q4_K_M）。
    2. 
    
  2. 在电脑上用真实的槽位语料评估：槽位级 F1、整句完全匹配率、首 token 延迟。
    3. 
    
  3. 把模型文件放到应用私有目录或随 APK 分发（注意 APK 体积限制，大模型建议首次启动时下载或由用户导入）。
    4. 
  

  
第二步：在设备上启动 llama-server

  

  
第三步：Schema 与约束

  
Schema 同时用于约束解码和代码校验。约束保证“结构和枚举”正确，代码校验保证“业务含义”正确（例如日期是否真实存在、人数是否超过上限）。

  
第四步：Android 端调用（Kotlin）

  

    HTTP 调用在后台线程执行（withContext(Dispatchers.IO)），不要阻塞主线程。
    
  

  

  
第五步：多轮对话与追问

  
状态只保存非空值；缺失的槽位只追问第一个；全部满足后在本地执行业务动作。用户切换意图时清空旧槽位。
